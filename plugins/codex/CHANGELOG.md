# Changelog

## Unreleased

- Add `task --scratch-sandbox`: runs Codex with a `workspace-write` sandbox rooted at a persistent, per-repository scratch directory instead of the repository itself (TEMP/TMP are also pointed there), so tempfile-based tests (`tempfile.TemporaryDirectory`, `mkdtemp`, …) get a writable temp directory even under an otherwise read-only review — on Windows a `read-only` sandbox denies writes everywhere, including `%TEMP%`, which previously made a reviewer judge tests by the author's description instead of actually running them. The repository stays read-only and reachable only via `cd <repo>` (a preamble prepended to the prompt says so); the scratch directory is the sole writable root (`sandbox_workspace_write.writable_roots`, with `network_access`/`exclude_tmpdir_env_var`/`exclude_slash_tmp` pinned explicitly rather than left to host config defaults), never the repository. The app-server's ACTUAL `thread/start` response is checked against that policy (cwd, sandbox type, network access, writable roots) before `turn/start` is ever sent — a mismatch fails the job closed instead of silently running with a weaker guarantee. The scratch directory's path is stable per repository and only its contents are cleared before each run — not recreated — so Codex's Windows sandbox reuses the synthetic SID it already granted that path instead of minting (and leaking) a new one every run; that clear is itself guarded against a symlink/junction on the path and against the plugin's state directory (or the scratch directory itself) resolving inside the repository, and access to it is serialized across concurrent runs on the same repository with an interprocess lock (`CODEX_COMPANION_SCRATCH_LOCK_TIMEOUT_MS`/`..._POLL_INTERVAL_MS` override the 10-minute/2s defaults). Self-contained: rejects `--write` (contradicts the repository staying read-only), `--read-only` (a different sandbox mechanism achieving the same read-only repository — combining them asks for two sandbox modes on one thread), and `--resume`/`--resume-last` (a resumed thread keeps its own sandbox policy, so the flag's guarantee cannot be kept on it) — all refused before any app-server call. Job bookkeeping (`status`/`result`) stays keyed by the repository, exactly as without the flag; `result --json` additionally carries `sandboxEffective`, the actually-resolved policy.
- Harden `--scratch-sandbox`'s safety checks after further review:
  - The junction/reparse-point check on the scratch directory's path (`assertPathIsPlainDescendant`) now also covers the plugin's own STATE directory itself, not just the path below it — previously a junction sitting exactly at the state directory's own slot, whose target already happened to contain a `scratch` subdirectory, could sail through the old check while every subsequent read/write/delete actually landed in the junction's target.
  - The remaining gap after that fix — a race between the check and the destructive clear, on the path components above the scratch directory — is a threat-model tradeoff, not a bug: inside the sandboxed Codex turn, only the scratch directory itself is writable, so a process running inside that sandbox cannot touch anything above it to race this window at all; a process outside the sandbox racing it already has unrestricted filesystem access regardless. Documented in code as such, next to the check.
  - Reclaiming a lock whose recorded pid died is now atomic: the stale lock file is `renameSync`'d to a unique staging name first (exactly one racer's rename can succeed on a given source path; every other loses with `ENOENT` and retries) rather than unlinked and recreated, which let two processes that both observed the same dead-pid lock each believe they held it afterward. The rename winner also verifies, by reading back the staging file, that what it actually moved still matches what it originally judged stale (pid/jobId/startedAt) before publishing its own lock — without this, a takeover delayed long enough for a genuinely concurrent racer to have already published ITS OWN fresh lock in the meantime could silently steal that live lock instead of just losing the race to it; a mismatch puts the file back (best-effort) and retries instead.
  - A lock is now also judged stale when its recorded `jobId` corresponds to a job already in a terminal status (or missing from the job index entirely) — not just when its `pid` is dead — since an OS pid can be reused by an unrelated process after the original holder exits, which would otherwise make the lock look permanently held. A worker that dies mid-run in a way that leaves its own job record stuck `running` without the pid actually staying alive is a known, deliberately unclosed gap: the next `--scratch-sandbox` run on that repository waits out the lock timeout and fails with a clear "busy with job …" error rather than corrupting anything.

- Add `--output-schema <path>` to `task`: a JSON Schema is read and parsed once, up front (same one-shot timing as `--prompt-file` — a missing or malformed schema throws before a background job is queued or a foreground turn is spent, and never touches a pending `--prompt-file`), then forwarded as `turn/start`'s `outputSchema` for both a fresh and a `--resume-last`/`--resume` turn. `task`'s stdout is unchanged either way — Codex's final message prints as usual — but with `--output-schema` set, `task --json`, `result --json`, and the stored job record also carry the parsed answer as `structured` (`structuredError` set and `structured: null` when Codex's answer does not parse as JSON against the schema), reusing `parseStructuredOutput` from `lib/structured-output.mjs` rather than a second parser. Without the flag, `task`'s payload gains no new keys.
- Add `prompt-path` to `codex-companion.mjs`, printing a fresh, not-yet-existing file path under the plugin's state directory, and route the `codex-rescue` subagent's prompt delivery through `Write` + `task --prompt-file` instead of an inline Bash argument. A measured 30.6% of `codex-rescue` runs (57 of 186) failed from the prompt riding inline in the `task` command string (shell EOF, the Bash-command-length gate, a trailing backslash eating a quote); the equivalent flow via `--prompt-file` had 0 failures in 22 runs.
- `task --prompt-file <path>` deletes that one-shot file once the task it was read for is actually accepted (the background job is durably queued, or the foreground run passed every precondition and actually executed) — not immediately on read, so a run that fails a precondition (flag conflict, Codex unavailable, `--resume-last` with no prior thread) leaves the prompt file in place for a retry. Deletion additionally requires the file to be inside the prompts directory `prompt-path` handed out (verified via `fs.realpathSync` on both, not a string prefix — case-insensitively on Windows, where a drive letter's case is not significant), to be a regular file and not a symlink (`fs.lstatSync`), and to match the exact `<label>-<uuid>.md` naming `prompt-path` generates — a caller's own file, anywhere or anyhow named, is never touched. Both `prompt-path` and `task --prompt-file` also sweep prompt files older than 7 days, restricted to that same naming pattern. The prompts directory is created `0o700` on POSIX (fail-closed: an error narrowing it throws rather than silently serving prompt files from a directory of unknown permissions); on Windows, ACL inheritance is left as-is and the near-immediate deletion after read stands in for directory-level isolation instead. The prompts directory itself is verified before every read/write/delete through it — not a symlink or Windows junction, and its realpath actually lands inside the state directory's realpath — `prompt-path` fails closed (refuses to hand out a path) if that verification fails, while `task`'s cleanup only warns on stderr and skips both the delete and the age sweep, since housekeeping must never turn an already-accepted task into a reported failure. Any other unexpected cleanup error is likewise caught and downgraded to a stderr warning, never allowed to cost the caller their jobId.
- Document `--prompt-file` in `task`'s usage line (the flag already worked; it just was not discoverable).
- Stop an orphaned shared Codex app-server broker after 15 minutes with no connected clients. Active foreground and background jobs keep their broker connection open, and the timeout can be configured with `CODEX_COMPANION_BROKER_IDLE_TIMEOUT_MS` (`0` disables the safety timer).
- Close the broker listener before asynchronous child cleanup and safely reject reconnects already queued during shutdown.
- Allow the spawned `codex app-server` handshake deadline (default 10 seconds) to be raised with `CODEX_COMPANION_SPAWNED_INITIALIZE_TIMEOUT_MS`, for cold starts and heavily loaded or CPU-limited machines, and name both the deadline and that override in the timeout error message.
